## Goal

Build a corpus of **real photographs** with human-verified ground truth, so that a working
detection model scores meaningfully above a broken one. Today both score 0.0%.

## Why the existing corpus cannot be extended

`test-data/cv/` is generated by `scripts/generate-cv-images.mjs`, which draws *"furniture as
solid palette-coloured rectangles (the colours the mock [detector] expects)"* (`:7`). Ground
truth in `expected.json` labels those rectangles `lamp`, `shelf`, `sofa` and so on.

It is a correct fixture for the mock engine and a genuine pipeline regression test. It is
unusable for ranking vision models, because the images do not depict what the labels claim.
Measured 2026-08-18 with a driver known to work:

```
[eval-cv] precision 0.0%  recall 0.0%  meanIoU 0.000  labelAcc 0.0%
```

No amount of tuning fixes that — the images would have to become photographs, at which point
the mock engine (which matches colours to labels) stops scoring ~1.0 and its regression test
is lost. **Both corpora are needed, for different jobs.** This ticket adds one; ticket 0002
keeps the other honest about its purpose.

## Sourcing the images

Three options, in rough order of preference:

1. **Real captures from ordinary use.** Best fidelity — actual camera, actual lighting,
   actual framing, actual motion blur. Requires wave 04 ticket 0003, since captures are
   currently destroyed unless inference succeeds. This is the durable answer.
2. **Hand-shot photographs** of the same spaces, taken deliberately for the corpus. Works
   today, no dependency. Risks being cleaner and better-framed than real captures, which
   would make the corpus flatteringly easy.
3. **A public dataset** with existing annotations. Cheapest, but the label vocabulary will
   not match `SPATIAL_DETECTION_PROMPT`'s ("the single most specific singular noun … sofa,
   chair, table, desk, tv, monitor, lamp …"), and licence terms need checking before
   anything enters the repo.

Whatever the source, **the images must look like what the scanner actually produces**:
1280 px long edge, JPEG quality 0.8 (`src/capture/capture.ts:21-23`), handheld framing,
mixed lighting. A corpus of well-lit product photography would measure the wrong thing.

## Ground truth

Human-verified, and the verification recorded. Concretely:

- Labels drawn from the same vocabulary the prompt asks for, so a correct answer is not
  marked wrong for saying `monitor` where truth says `screen`. Synonym handling is a real
  design question — see Open questions.
- Bounding boxes as 0-1 fractions, matching `RawDetection.bbox` — reuse the existing shape,
  do not invent a second one.
- Same `expected.json` schema as `test-data/cv/` so `eval-cv.mjs` can score either corpus
  without a second scorer.
- **Who verified each image, and when.** Ground truth that nobody will vouch for is how this
  problem recurs.

## Non-goals

- Do not delete or regenerate `test-data/cv/`. It is the mock engine's regression fixture
  and it works. Ticket 0002 clarifies its role.
- Do not change `eval-cv.mjs`'s scoring maths (greedy IoU matching, precision/recall/IoU/
  label accuracy). The metrics are fine; the inputs were not.
- Do not build a labelling UI. Hand-authored JSON against a checked-in image set is
  sufficient at this size and avoids inventing a tool.
- Do not gate CI on the new corpus in this ticket. That is 0003, after a baseline exists.
- Do not tune the prompt or the model against the corpus while building it. A corpus
  authored to make the current model look good measures nothing.

## Open questions & answers

- Q: How many images? — OPEN. Enough that one lucky guess does not move the score, few
  enough to verify by hand. 30-50 is the instinct; **decide against how long a full run
  takes** — the ONNX driver averaged ~12 s per image, so 50 images is ~10 minutes per model.
- Q: How are synonyms handled? — **OPEN and important.** `monitor` vs `screen` vs `display`,
  `sofa` vs `couch`. A strict string match will punish correct answers and make the score
  unreadable. Options: an explicit synonym table in the fixture, or accepting any label from
  a per-object allowed set. Leaning allowed-set, because it makes the ground truth honest
  about ambiguity rather than hiding it in scorer logic.
- Q: Do we score descriptions at all? — OPEN. `description` is free text and hard to score,
  but it is where the model demonstrates it actually looked ("white ceramic mug on saucer").
  Probably out of scope for a numeric score; possibly worth recording for human review.
- Q: Where do the images live — in-repo or fetched? — OPEN. In-repo is simplest and makes CI
  trivial; 50 JPEGs at ~140 KB is ~7 MB, which is acceptable. Check against repo-size norms
  before committing to it.
- Q: Privacy — do real captures of a real home belong in a git repo? — **OPEN, and must be
  answered before any capture-sourced image is committed.** This is a scanner for people's
  homes. Staged spaces or explicit consent, recorded.

## Schema required

Reuses `test-data/cv/expected.json`'s shape exactly:

```json
{ "file": "...", "width": 0, "height": 0,
  "detections": [ { "label": "...", "bbox": [0,0,0,0] } ] }
```

Plus, per the synonym question, possibly `acceptableLabels: ["monitor","screen"]` per
detection — an addition to the shape, not a replacement, so `eval-cv.mjs` keeps working
against the synthetic corpus unchanged.

## Acceptance Criteria

- [ ] Given the corpus and a working model, Then the score is well above zero
- [ ] Given the corpus and `moondream:latest`, Then the score is near zero
- [ ] Given those two runs, Then the difference is large enough to rank models by
- [ ] Given the synthetic corpus, Then the mock engine still scores ~1.0 (unbroken)

## Risks / potential issues

- **Risk:** A corpus authored by the same judgement that picks the model bakes in that
  judgement's blind spots. — **Mitigation:** Ground truth is written from the photograph, by
  a human, *before* seeing any model output. Never adjust truth to match a model.
- **Risk:** Real captures of real homes are personal data. — **Mitigation:** Explicit open
  question; must be answered before committing any such image.
- **Risk:** Synonym handling makes the score either punitive or meaningless. —
  **Mitigation:** The allowed-set approach, decided explicitly rather than emerging from
  scorer tweaks.
- **Risk:** The corpus is too small and the score is noise. — **Mitigation:** The
  known-good vs known-bad gap in Tests is the check; if it is not large and stable, the
  corpus is not finished.
- **Risk:** ~10 minutes per model per run discourages use. — **Mitigation:** Acceptable for
  a pre-merge gate; 0003 decides what runs in CI versus on demand.
