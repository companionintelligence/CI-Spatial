Companion Scan, mapped

A browser-based AR room scanner: point your phone at a room over Tailscale, and a Deno server turns the walk-through into a labelled 3D world — point clouds, Gaussian splats, and a shared multi-scan editor. This atlas indexes every feature, the data it moves, the variables that steer it, and how its pieces actually talk to each other, built by reading the source directly rather than the docs.

Living document — docs/factory/atlas.html, versioned by git. 05-on-device-inference

4 / 4 done
docs/factory/05-on-device-inference/
0001 extract driver ✓, 0002 provision weights ✓, 0003 WebGPU runtime ✓, 0004 ungate + fallback policy ✓

Makes the WebGPU inference toggle real, rather than deleting it. The product offers "On-device — no data leaves your phone" and had never been able to honour it: no released Transformers.js registers the pipeline task the worker asks for. Porting was chosen over removal deliberately — the claim is strategic to a product whose tagline is "Private spatial memory for places you own," and most of the work already existed, since server/inference.ts already drove LFM2.5-VL by hand. Ticket 0001 lifted that loop out into a runtime-agnostic driver (src/inference/lfm-driver.ts) behind a 4-function port, with the Deno/onnxruntime-node path (server/lfm-driver-onnx.ts) as its first consumer and verified byte-identical detections on real photographs before/after. Ticket 0002 answered the wave's go/no-go question — measured on a Lume Pad 2: 2.2 GB of weights (not the ~1.5 GB previously documented), a 10.04 GB origin quota, 21.6 MB/s over a warm tailnet (~104 s full transfer), and a grantable persist() — and shipped src/inference/model-provisioning.ts: resumable, verified, IndexedDB-cached downloads with an explicit opt-in affordance, so a partial or corrupt transfer is never handed to the runtime and scan data is never evicted to make room. Ticket 0003 added the browser half — src/inference/lfm-driver-web.ts implements 0001's port against onnxruntime-web's WebGPU execution provider (pinned to the 1.21.x line to match onnxruntime-node's major), reading 0002's IndexedDB cache directly via SessionOptions.externalData rather than re-fetching, with the WASM/JSEP runtime copied to public/ort/ at postinstall so no third-party request happens. Parsing the actual downloaded weights found the largest single tensor — decoder_q4.onnx's tied embed_tokens.weight — at exactly 512.00 MiB, precisely the Adreno adapter's maxStorageBufferBindingSize from ticket 0003's own measurement, not comfortably under it; real on-device confirmation on the Lume Pad 2, plus the latency/memory measurement, remained a manual step 0003 could not close from a workstation. Ticket 0004 removed WEBGPU_INFERENCE_ENABLED — the toggle is offered wherever InferenceRouter.hasWebGPU (a live navigator.gpu check, not a build flag) is true, disabled with a specific reason otherwise — and fixed the one defect that mattered most: infer()'s timeout branch used to fall back to the server silently once a request ran long, so a capture the panel labelled "On-device" could still leave the phone without saying so. Both the timeout branch and the worker-error branch now reject with a typed WebGpuInferenceError instead — the capture fails, the frame is kept (wave 04 ticket 0003's capture record), and the HUD says specifically why. That record also now carries which engine each capture was sent to, so a scan mixing server and on-device detections is legible instead of opaque.

Impact: the toggle wave 04 gated is a real capability — the same model running in the browser on onnxruntime-web, offered only where it can work, and failing honestly (never a silent server upload) where it can't.

06-detection-ground-truth

0 / 3 done
docs/factory/06-detection-ground-truth/
real corpus → retarget eval/bench → regression gate

Nothing in this repo can tell whether object detection works. Measured 2026-08-18: a driver that correctly identified a mug, two keyboards, a monitor, a tripod and handwritten paper on a real photograph scores 0.0% precision, 0.0% recall and 0.000 mean IoU on npm run eval:cv, across all 16 corpus images — because the corpus is solid palette-coloured rectangles built for the deterministic mock detector. It is a good pipeline regression test and cannot be a test of whether a vision model sees things. README.md nonetheless tells you to pick your model with it.

Impact once shipped: model choice stops being ranked against a fixture that punishes working models, and a detection regression becomes something CI can actually catch.

07-scan-identity

4 / 4 done
docs/factory/07-scan-identity/
unique scanId + migration → one session identity → node provenance → pipeline guard

Four tickets on one question the system cannot answer: which scan is this? A scan's id is derived from the capture session, a capture session is one browser tab, and a tab produces many uploads — so every autosave in a walkthrough collides onto one id. Observed 2026-08-19: worlds/default.json holds four distinct GLBs under one scanId, and the viewer discards three of them at load while the HUD reports "1 scan loaded". Edit-patch replay, memory-push idempotency and job GC all resolve to whichever scan they find first.

Impact once shipped: every uploaded scan exists, loads and toggles independently; keyframe jobs fail at preflight with a reason instead of inside the runner; and every node in an exported GLB records which session and capture produced it — which is what makes a later merged per-place GLB reversible.

09-ground-anchor-calibration

8 / 9 done
docs/factory/09-ground-anchor-calibration/
0001 honesty ✓, 0003 ground plane ✓, 0004 two-point flow ✓, 0005 tests ✓, 0006 benchmark instrument ✓, 0007 reference photos ✓, 0008 floor plane fit ✓, 0009 session frame bearing ✓ — the wave's code is done; its on-device measurements are not

Makes a Place's calibration frame measurably repeatable. PR #141 replaced the three-point reference triangle with one ground tap plus a compass bearing — the right interaction, but it left the frame's entire orientation resting on an indoor magnetometer (bearingDeg ?? 0 silently yields yaw 0 with no fix, so two sessions of one room can be rotationally misaligned by an unknown amount and stored as valid), and it kept reporting 'verified' after removing the check that word referred to. The claim was first made honest — every calibration reported 'provisional', with 'verified' left without a producer. Ticket 0004 then restored that producer by measurement: two ground markers on an established plane fix origin, heading and floor from geometry, and their separation is a room-intrinsic distance a later visit must reproduce within toleranceM before anything is called verified. Governed by ADR 0005 — geometry for relative alignment, compass for absolute orientation.

Impact once shipped: orientation stops depending on the least reliable sensor on the device; repeat visits get a real residual again, at two taps instead of the original three; project-space y = 0 becomes the room's floor rather than wherever the first tap landed; the calibrationResidualM sidecar key carries a real value again instead of null. The tolerance constants were not measured: ticket 0006 shipped its instrument but was closed without running the benchmark, so DEFAULT_SEPARATION_TOLERANCE_M, MIN_POINT_SEPARATION_M and GROUND_TAP_TOLERANCE_M are adopted defaults with revisit triggers recorded at each definition.

Landed so far: the false 'verified' claim is gone (0001); the point cloud now tracks a lock-checked ground plane that gates readiness and rejects off-floor taps (0003); anchorToProjectTransform() and buildAnchorMarker() have unit coverage where they had none (0005); and the scanner HUD has a debug-gated pose/drift readout with a written room-loop procedure (0006).

Still unmeasured, and the atlas will not pretend otherwise: 0006 shipped the instrument, not the measurement. Nobody has walked the room loop, so GROUND_TAP_TOLERANCE_M = 0.25 is still the guess it was, and 0002's DEFAULT_SEPARATION_TOLERANCE_M / MIN_POINT_SEPARATION_M are unwritten proposals. ADR 0005 rule 5 says a tolerance must cite a measurement; none of these can yet. Scheduling that run surfaced a second finding: 0006's Procedure 2 reads a separationM that only ticket 0004 produces, so it cannot supply the constant 0002 needs — ../testing/DEVICE_TESTING.md now carries a Procedure 2a that measures the same quantity on the build that shipped. The WebXR anchor-decal verification 0005 asks for (../testing/DEVICE_TESTING.md § B2) is likewise unrun — it needs an ARCore Android device, and no unit test reaches that renderer.

10-4d-person-capture

8 / 8 done
docs/factory/10-4d-person-capture/
0001 takes + N-member rooms ✓, 0002 measured sync ✓, 0003 recorder ✓, 0004 durable clips ✓, 0005 frame-set contract + job ✓, 0006 subsystem ✓, 0007 splat4d playback ✓, 0008 ADR/docs/atlas ✓ — the wave's code is done; the 4DAnyone stage is unrun

Teaches Companion Scan to capture a person, not just the room around them. 4DAnyone turns a casual monocular video of a person into the multi-view video a calibrated camera array would have recorded; this wave adds the capture and playback halves and puts the inference behind a subsystem boundary. The organising idea is that 4DAnyone is a view-densifier standing in for cameras you didn't have — with N synchronized phones you already have real views and skip it; with one phone it synthesizes the rest. Both paths converge on one artifact, a per-timestep set of posed multi-view frames, which is exactly the shape splat_train_dataset.ts already builds for Brush. That convergence is what makes the densifier swappable rather than a dependency.

The best reuse in the wave is ADR 0005. Two phones that tap the same two ground markers are, by construction, in the same project frame — which is precisely the extrinsics a multi-camera rig needs. The wave adds no calibration mechanism; src/ar/project-calibration.ts is the rig calibration. It also adds the first video recording this app has ever had: MediaRecorder appears zero times in the repo today.

Why the inference is not on the appliance, measured rather than assumed: 4DAnyone needs 43.3 GiB peak on one CUDA device and 8–26 min per clip. Probed on the tailnet 2026-08-24, beta-1 is 2× Radeon RX 7900 XTX at 23.98 GiB each on ROCm with no CUDA, and beta-red is a 10 GiB RTX 3080. Nothing on the fleet qualifies — a ~1.8× per-device shortfall against a model that does not shard across cards, on the wrong vendor's stack. So the heavy stages live in subsystems/4d-capture/, and the appliance's driver reports skipped + a remediation string when no host is configured, exactly as BRUSH_BIN and LINGBOT_MAP_* already do.

Two constraints the atlas will not soften: the 4DAnyone path is unverifiable until a qualifying GPU exists, so ticket 0006 ships stub mode as a first-class feature and its badge stays 🔜 pending GPU host rather than done. And the shipped weights are mixed-licence — GVHMR, a mandatory pipeline stage, is research/non-profit only and YOLOv8 is AGPL-3.0, against this repo's commercial LICENSE.md. Ticket 0008 records that constraint in ADR 0006; it does not resolve it.

11-panoramic-canvas

0 / 7 done
docs/factory/11-panoramic-canvas/
0001 measure the backbone → 0002 implement depth-reconstruct → 0003 the canvas + contract → 0004 frame selection → 0005 ask the canvas → 0006 the editor surface → 0007 ADR/docs/atlas

Gives a scanned Place one image of itself — an occlusion-free equirectangular panorama reprojected from the posed keyframes a scan already carries — and lets the VLM already running here answer questions about the whole room from it. The idea is OneCanvas (TUM + Huawei, arXiv:2606.19253): unproject patch features from many posed views, reproject onto one panoramic canvas, hand it to a standard pretrained VLM as a single image — no geometry encoder, no architectural surgery.

Its code is unreleased ("The code is not released yet"), so the wave is shaped like 10-4d-person-capture: build the contract and everything around it, ship value without the framework, leave a drop-in point. The canvas construction needs none of their code — it is fully specified in the paper. What the unreleased weights provide is the trained adapter that reads a feature canvas, so the geometry is built now against RGB, which is independently useful: one image of a whole room, handed to the qwen3-vl already running, answers whole-scene questions per-frame inference cannot.

The fit is unusually good, and mostly because the repo already anticipated it. Posed keyframes, deriveIntrinsics() (which already converts fovY+aspect to fx/fy/cx/cy with rescaling), and a qwen3-vl default are all here. Depth is the one missing input — and depth-reconstruct, LayerType.'depth' and FrameObservation.depthUrl have been declared with no producer since the job systems merged. Ticket 0002 finally supplies one.

Unlike wave 10, it may run on the fleet. 4DAnyone needed 43.3 GiB on one CUDA device and nothing came close; OneCanvas inference is Qwen3-VL-8B with a frozen encoder and LoRA — plausibly ~16 GB, against beta-1's 23.98 GiB. Plausible, not established: the paper reports training compute and no inference figure, so ticket 0001 is a measurement that decides on-fleet vs off-box before anything is built on the guess.

The first three waves don't change what the system does. Every ticket across foundation-updates, 01-merge-jobs and 02-typed-event-payloads preserves current behavior — wire formats, on-disk formats, storage keys, and defaults stay byte-identical. That is the "harden" half of "unify and harden the repo," not a feature wave. (Two behavior changes did land alongside 01-merge-jobs, both deliberate and both outside its tickets — see below.)

03-readiness-hardening is the exception, deliberately. It exists to fix defects, so three of its six tickets change observable behaviour: a transform patch starts applying to the node it was taken from (0004), GET /scans stops re-sweeping the sessions directory per scan (0005), and Leaflet stops being fetched from unpkg at runtime (0006). Wire formats and on-disk formats still stay byte-identical.

Project calibration (spatial frame)

Before scanning starts, the user marks a physical reference so every session of the same Place lands in one coordinate frame. Produces sessionToProject, which the server prefers over GPS placement when present. Two tiers. Two-point ground (default, ticket 0004) is staged: the ground plane must lock, then a landmark is placed and confirmed, then a heading marker at least MIN_POINT_SEPARATION_M away; both hits are snapped onto the established plane, so the baseline is horizontal and project-space y = 0 is the floor. Heading comes from the landmark→marker geometry, never the compass, so two sessions started at different device yaws produce the same frame. The pair's separationM is the invariant a later visit re-measures: within toleranceM reports 'verified', beyond it warns with the measured discrepancy and offers re-place or override. Spatial Reconstruction

A second, higher-fidelity pipeline that turns a session into a dense point cloud and a trained 3D Gaussian splat — each stage shells out to an external native tool and degrades to a "skipped" manifest instead of crashing when that tool is unavailable.

A splat has no metres until a device that measures acceleration supplies them. Monocular structure-from-motion is scale-blind: every stage from pose-solving to compression works in arbitrary units at an arbitrary origin. Orientation is recovered (COLMAP gravity-aligns to +Y up); size is not. The only true metric source in this system is the phone's IMU-aided visual-inertial odometry — the IMU measures real acceleration, so AR poses are in real metres. splat-align makes a distance real by fitting the splat against those poses. Calibration does not supply scale. anchorToProjectTransform passes scale 1 to composeYUpTransform — sessionToProject is a rigid yaw+translate that fixes origin, heading and the y=0 floor so two visits line up. And separationM is Math.hypot over two hit-test points, i.e. measured by the AR runtime in the AR runtime's units — there is no tape-measure input anywhere in the flow. It earns its keep as a cross-session repeatability check, not as a physical ruler. Anything reading dimensions off a capture with no AR poses is reading unitless numbers.
