# Real-photograph corpus

> Ticket: [`docs/factory/06-detection-ground-truth/0001-real-photograph-corpus.md`](../../docs/factory/06-detection-ground-truth/0001-real-photograph-corpus.md)
> ADR: [`docs/adr/0001-reuse-existing-domain-model.md`](../../docs/adr/0001-reuse-existing-domain-model.md)

**Status as of 2026-08-24: scaffolding and policy only. No photographs have been taken
yet.** `expected.json` in this directory is a valid, empty instance of the schema below —
zero entries, not zero true objects. See [Manual step remaining](#manual-step-remaining).

This directory sits **beside** `test-data/cv/` (the synthetic, mock-engine fixture
generated by `npm run gen:test-data`), not inside it. `test-data/cv/` stays exactly as it
is — see `docs/factory/06-detection-ground-truth/0002-retarget-eval-and-bench.md` for why
both corpora are needed and for different jobs.

Unlike `test-data/cv/`, this directory **is checked in**, not generated — see the
`.gitignore` exception at repo root (`!test-data/real/`, `!test-data/real/**`).

## Why this exists

`test-data/cv/` draws furniture as solid palette-coloured rectangles so the deterministic
mock engine can match colours to labels. No photo-trained vision model will ever call a
brown rectangle a "chair" — measured 2026-08-18, a driver that correctly named a mug, two
keyboards, a monitor, a tripod and a handwritten note on a real photograph scored 0.0%
precision/recall/label-accuracy against that corpus, identical to a model that fabricates
every detection. The harness could not tell a working model from a broken one. This corpus
is the fix: real photographs, human-verified ground truth, so a working model scores
materially above zero and a fabricating one does not.

## Decisions (this ticket)

### 1. Sourcing option

**Chosen: hand-shot photographs (ticket's option 2), deliberately composed to match real
capture conditions.**

Wave 04 ticket 0003 (`fix(capture): persist the frame before inference runs`, merged as
[#117](https://github.com/companionintelligence/CI-Spatial/pull/117)) has landed, so
option 1 (sampling frames from ordinary real captures) is no longer blocked by captures
being destroyed on inference failure. It is still blocked by two things this ticket does
not solve: (a) `CaptureRecord.blob` lives client-side in IndexedDB
(`src/scene/store.ts:85-93`) with no export path to pull frames out for a corpus, and (b)
someone has to physically walk a real space with the AR scanner. Neither is something this
change can do from a repo checkout.

So the near-term corpus is hand-shot: a phone camera, framed and encoded the same way the
scanner would (§3), of real staged objects — not product photography. To avoid the
ticket's named risk ("cleaner and better-framed than real captures, making the corpus
flatteringly easy"), each shot must vary at least one of: off-axis framing (not
square-on), mixed/uneven lighting (not a lightbox), partial occlusion, and visual clutter
typical of a lived-in room. A shot-composition checklist lives in §5.

**Revisit when real captures accumulate.** Once retention has enough ordinary-use history
and an export path exists, graduate to sampling real captures (option 1) as the durable
source, keeping the hand-shot set as a supplement rather than replacing it outright —
don't discard a working fixture to chase a purer one.

Option 3 (a public annotated dataset) was not chosen: licence terms would need clearing
before anything enters the repo, and the label vocabulary and framing (product photography
vs. handheld, mixed-lighting scanner captures) would not match what this corpus needs to
measure.

### 2. Privacy — decided before any image is committed

- **Staged spaces only**, photographed specifically for this corpus. No photographs of a
  real user's home, workplace, or any space captured incidentally during ordinary product
  use.
- **No identifiable people** in frame — no faces, no visible screens/documents/mail
  carrying anyone's personal information.
- If a future contribution genuinely needs a personally-owned space (closer to what the
  scanner sees in the wild), it requires the space-owner's **explicit, recorded consent**
  — a `consent` note naming who consented and when, held alongside that image's
  `verifiedBy`/`verifiedAt` (§4) — before the image is committed. No such image exists in
  this corpus today; staged spaces are sufficient for the hand-shot sourcing option above.

### 3. Capture-matched encoding

Every image must match what `src/capture/capture.ts:21-30` actually produces:

- **1280 px long edge** (`maxLongEdgePx`, `capture.ts:29`)
- **JPEG quality 0.8** (`jpegQuality`, `capture.ts:30`)
- Handheld framing (not a tripod square-on shot), mixed/ambient lighting (not a lightbox)

A corpus of well-lit product photography measures the wrong thing — see the ticket's
Sourcing section.

### 4. Ground truth & verification

- Ground truth is written **from the photograph, by a human, before seeing any model
  output.** Never adjust truth to match a model's answer — see the ticket's first Risk.
- Each entry records **who verified it and when** (`verifiedBy`, `verifiedAt` — additive
  fields, §6). Ground truth nobody will vouch for is how this problem recurs.
- Labels are drawn from the vocabulary `SPATIAL_DETECTION_PROMPT` actually asks for
  (`src/inference/prompt.ts`'s `CORE_LABELS`, or "another single general noun" per the
  prompt's own fallback) — not an ad-hoc vocabulary invented for the fixture.
- Bounding boxes are `[x_min, y_min, x_max, y_max]` as 0-1 fractions of image width/height
  — `RawDetection.bbox`'s convention (`src/inference/prompt.ts`), reused verbatim.

### 5. Corpus size

**Target: 40 images.** Reasoning:

- Within the ticket's own instinct range (30-50): enough that one lucky guess does not
  move the score, few enough to verify by hand.
- Each image typically holds several objects (the working-driver example above found five
  in one photo), so 40 images yields on the order of 150-200 individual ground-truth boxes
  — the score is not decided by any single image.
- Per-run cost: the ticket records the ONNX driver at ~12 s/image, so 40 images is ~8
  minutes per model — inside the ~10-minute figure the ticket calls acceptable for a
  pre-merge gate (wave 06 ticket 0003 decides what actually runs in CI vs. on demand).

Shot-composition checklist per image (at least one must apply, ideally more):
off-axis angle, mixed/uneven lighting, partial occlusion of at least one object, ordinary
household/office clutter in frame. Spread the 40 across enough distinct staged spaces
that the corpus is not effectively one room photographed 40 times.

### 6. Synonym policy

**Decided: allowed-set, not a synonym table.** An optional `acceptableLabels` array on a
detection lists other single-noun labels a correct answer may use instead of `label` — an
**additive** field, so `test-data/cv/expected.json` and `eval-cv.mjs`'s current
`entry.detections` / `d.label` / `d.bbox` reads are unaffected (`eval-cv.mjs:59-98`
already ignores any keys it doesn't read). Wiring `acceptableLabels` into the actual
match/score logic is explicitly **out of scope here** — this ticket's non-goals rule out
changing `eval-cv.mjs`'s scoring maths, and wave 06 ticket 0002 is the one retargeting the
harness; it should honour this field when it does.

Ground truth's canonical `label` is always the term a correct human description would use
first (typically a `CORE_LABELS` entry); `acceptableLabels` is only for genuine, named
ambiguity — e.g. `monitor` vs `screen` vs `display`, `sofa` vs `couch` — added
deliberately per detection, not as a blanket escape hatch. An empty/absent
`acceptableLabels` means strict match against `label`.

Descriptions (`description` in a `RawDetection`) are **not scored** by this corpus — free
text is hard to score numerically, and the ticket leaves this an open question. Human
reviewers may still read a model's `description` output against the photograph when
diagnosing a bad score; nothing in this fixture depends on it.

## Manual step remaining

**Taking the photographs, and authoring + verifying the ground truth against them, is a
physical/human step this change cannot perform** — it requires a real camera, real staged
objects, and a human looking at each photograph to write down what's actually in it. That
step, and the resulting "known-good vs. known-bad" model runs the ticket's Tests section
asks for, are not done. Everything else the ticket asks this piece to decide and document
— sourcing, privacy, encoding, verification protocol, corpus size, synonym policy, and the
schema itself — is decided and recorded above and in `expected.json`'s shape (§ below).

To finish the corpus once photographs exist:

1. Shoot ~40 images per §5's checklist, matching §3's encoding, saved as
   `real-<NN>-<slug>.jpg` (mirroring `test-data/cv/`'s `cv-<NN>-<slug>.jpg` naming) in
   this directory.
2. For each image, write a human-authored entry into `expected.json` per the schema below
   — looking only at the photograph, before running any model against it.
3. Run `qwen3-vl:4b` (known good) and `moondream:latest` (known fabricating) against the
   populated corpus and record both scores. A large, stable gap between them is the
   corpus's actual validation (per the ticket's Tests section) — a small or unstable gap
   means the corpus isn't finished, not that scoring wiring (0002) is broken.
4. Update this file's Status line and the checkboxes in
   `docs/factory/06-detection-ground-truth/0001-real-photograph-corpus.md`.

## Schema

Reuses `test-data/cv/expected.json`'s shape **verbatim**, plus additive fields (existing
consumers that only read `file`/`width`/`height`/`detections`/`label`/`bbox` are
unaffected):

```json
[
  {
    "file": "real-00-example.jpg",
    "width": 1280,
    "height": 960,
    "verifiedBy": "name or email of the human who wrote this entry",
    "verifiedAt": "2026-08-24",
    "detections": [
      {
        "label": "monitor",
        "bbox": [0.12, 0.18, 0.61, 0.74],
        "acceptableLabels": ["screen", "display"]
      }
    ]
  }
]
```

- `file`, `width`, `height`, `detections[].label`, `detections[].bbox` — unchanged from
  `test-data/cv/expected.json`.
- `verifiedBy` / `verifiedAt` — new, per image. Who verified this entry's ground truth,
  and when (ISO 8601 date). Required for every entry before it is considered part of the
  corpus.
- `detections[].acceptableLabels` — new, per detection, optional. See §6. Omit entirely
  when `label` is unambiguous.
